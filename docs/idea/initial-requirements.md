# Yomikiri - アイデアメモ

## このドキュメントの位置づけ

このドキュメントは壁打ち・ブレストの成果物で、正式な仕様書ではありません。

## プロダクトビジョン

技術書やビジネス書の「積読（つんどく）」に特化した読書管理アプリ。本に**賞味期限（読了期限）**を設定し、期限から逆算した「今日のノルマ（必要ページ数）」を提示することで、読書を具体的な行動に落とし込む。

**一言で言うと**: 「積読」を「今日やること」に変換する読書管理アプリ

## 解決したい課題

### 今困っていること

1. **買って満足してしまう「積読」問題**
   - 良書と呼ばれる技術書を次々と購入
   - でもデスクの脇には手付かずの本が山積み
   - 一冊読み終える前に新しい本に目移りしてしまう
   - 結局どれも中途半端になって強い罪悪感

2. **「読みたい気持ち」と「読む行動」がつながらない**
   - 「いつか読もう」と思うだけで具体的なスケジュールがない
   - 忙しいとすぐに後回しになる
   - 期限がないから緊急性を感じない
   - 気づいたら3ヶ月放置

3. **既存の読書管理アプリは「記録」だけ**
   - ブクログやKindleは「読んだ本」を記録するのは得意
   - でも「これから読む本」を「読ませる」機能は弱い
   - 読書時間をスケジュールに組み込む機能がない
   - 結局「読みたい本リスト」が増えるだけ

4. **目標が曖昧で達成感がない**
   - 「この本を読む」というざっくりした目標
   - どこまで進んだか、あとどれくらいかが分かりにくい
   - 小さな達成感を感じられる仕組みがない
   - モチベーションが続かない

## ターゲットユーザー

### ペルソナ1: プログラミング初学者・現役エンジニア

- **年齢**: 20-35歳
- **職業**: エンジニア、エンジニアを目指す学習者
- **経験**: プログラミング学習中、または実務経験1-5年
- **今困ってること**:
  - 技術の進歩が速く、インプットすべき情報（本）が膨大
  - 学習すべき技術書が次々と増えて、優先順位がつけられない
  - 買った技術書が積読になり、「情報の賞味期限」が切れてしまう
  - 資格試験やポートフォリオ作成の期限があるのに、読書が進まない

- **欲しいもの**:
  - 技術書に「読了期限」を設定して、計画的に読み進める仕組み
  - 「今日は何ページ読めばいいか」が明確にわかるノルマ機能
  - 読書時間を先に確保できるカレンダー連携
  - 視覚的に期限の緊急度が分かるUI

### ペルソナ2: 資格試験や自己研鑽に励むビジネスパーソン

- **年齢**: 25-45歳
- **職業**: 会社員、フリーランス
- **特徴**: 資格取得や自己啓発に意欲的
- **今困ってること**:
  - 試験日までに参考書を読み終えたいのに、計画が立てられない
  - 仕事が忙しくて「いつか読もう」が続いてしまう
  - 高額な専門書を買ったのに、開いてすらいない罪悪感
  - 同僚や仲間と進捗を共有する場がない

- **欲しいもの**:
  - 試験日・目標日から逆算した読書計画
  - 忙しくても継続できる「今日のノルマ」提示
  - 読書時間を予定として確保できる仕組み
  - 仲間の進捗を見てモチベーションを保つ機能

### ペルソナ3: 「本を買って満足してしまう」自覚がある読書家

- **年齢**: 20-40歳
- **特徴**: 本が好きだが、収集自体が目的化している
- **今困ってること**:
  - 「買ったこと」に満足して、読まない本が増える
  - 未読本を「負債」として認識できていない
  - 買った本の存在を忘れてしまう
  - 同じような本を重複して買ってしまう

- **欲しいもの**:
  - 未読本を「賞味期限切れ」として可視化する機能
  - 期限が近づくと視覚的にプレッシャーを与えるUI
  - 読了したときの達成感を得られる仕組み
  - 購入前に「本当に読むか？」を考えるきっかけ

## 主要機能の候補

### P0 (MVPで絶対必要)

#### 1. 会員登録・ログイン
```
- Rails標準の認証（Devise等）によるアカウント管理
- メールアドレスとパスワードでログイン
```

#### 2. 積読の基本操作（CRUD）
```
- 積読登録: タイトル、総ページ数、読了対象ページ数、読了期限（賞味期限）
- 書影と著者は任意（未設定時はプレースホルダー表示）
- 積読一覧表示: 期限が近い順にソート
- 積読詳細: 進捗状況、ノルマ確認
- 積読編集・削除
```

#### 3. 進捗管理
```
- 基本は「今日読んだページ数」を入力 → 現在ページに自動反映
- ±ボタンで増減も可能
- 上級者向けに現在ページを直接入力することも可能
- 読書ステータス管理: 未読 / 読書中 / 読了（手動切替）
- 読了到達時は「読了にする」ボタンを強調表示
```

#### 4. ノルマ計算・表示
```
- 残ページ数・残日数から、1日あたりの必要ページ数を自動計算
- 計算式: N = ⌈P / D⌉（切り上げ）
  - P = 読了対象ページ数 - 現在ページ
  - D = 今日を含む残日数（期限当日はD=1）
- 更新タイミング:
  - 進捗更新時
  - 日付切り替わり時（毎日深夜の定期処理）
```

#### 5. 読了期限の変更（延長）
```
- 期限を変更可能（無制限）
- 延長回数は詳細画面に表示（"自分への言い訳"として可視化）
```

#### 6. Googleカレンダー連携（簡易版）
```
- 「Googleカレンダーに追加」ボタンを押すと予定作成画面へ遷移
- テンプレ入力済み: 予定タイトル / 説明文 / 所要時間
- 所要時間は15/30/45/60分から選択可能（初期値30分）
- 日時はユーザーが決定
- "都度追加"方式（繰り返し予定はGoogle側で設定可能）
- MVPではGoogle側の予定変更/削除は追跡しない
```

#### 7. 賞味期限ビジュアライザー（CSS版）
```
- 期限までの日数に応じて書影が色褪せる（filter: sepia + opacity調整）
- 段階:
  - 7日以下: セピア/透明度：弱
  - 3日以下: セピア/透明度：中
  - 1日以下: セピア/透明度：強
- 一覧を見ただけで「早く読まないとまずい本」が分かる
```

### P1 (重要だけど後回しでもいい - 本リリース)

#### 8. Googleカレンダー連携（自動版）
```
- OAuth認証後、ユーザー指定の読書可能時間帯に読書スロットを自動挿入
- 技術: omniauth-google-oauth2 / google-api-client
```

#### 9. 読書する曜日/頻度の設定
```
- 読む日（例: 月・水・金、または週3日）を設定
- その日数のみで逆算してノルマを計算
- より現実的な目標設定が可能に
```

#### 10. ISBN検索
```
- openBD APIで書籍情報を自動取得・補完（APIキー不要）
- 取得できない項目は手入力で補完
```

#### 11. メール通知機能
```
- ActionMailer + SendGridで賞味期限前のリマインド通知
- 期限3日前に「あと3日です」と通知
- 期限3日前の定義: (期限日 - 3日)のJST 00:00基準で判定し、同一ユーザー・同一本につき1回のみ発火
```

#### 12. 読了シェア機能（OGP対応）
```
- 読了時にOGPメタタグ付きのHTMLページを生成
- 表示例: タイトル / 読了までの日数 / 読了日 / 一言コメント（任意）
- SNSでシェアして達成感を共有
```

#### 13. 積読タイムライン機能
```
- 他のユーザーの積読状況や進捗を閲覧可能
- デフォルト非公開。本ごとに共有を明示的にONにした場合のみ表示
- 公開される情報: 本のタイトル・期限・進捗（%）のみ（メモ等は非公開）
- 表示名: ニックネーム表示（実名不要）
- 表示形式: イベント単位（新規登録時 / 期限3日前 / 読了時）
- 延長もイベント化して可視化
```

#### 14. 読書スピード計測
```
- タイマー機能で1ページあたりの読書時間を計測・保存
- ノルマ計算の精度を向上（時間⇄ページの換算）
```

#### 15. バックグラウンド処理
```
- GitHub Actions（cron）でrake taskを定期実行
  - ノルマ再計算
  - 期限イベント生成（期限3日前、読了など）
  - 通知対象抽出
- APIキー等はGitHub Secretsで管理
- 定期処理はJST基準（GitHub ActionsのcronはUTCのため換算）
```

### このツールの強み

1. **「記録」ではなく「予定化」まで面倒を見る**
   - 既存サービスは「読んだ本」のログが中心
   - 「読む行動」はユーザー任せ
   - Yomikiriは読書タスクを予定化し、「読む時間」を先に確保
   - MVPでも予定作成の手間を最小化、本リリースでは自動挿入で強制力を高める

2. **「期限」を"行動に変換できる形"で提示する**
   - ただ締切日を見せるだけでなく、「今日やるべき量」まで落とし込む
   - 残ページ数・残日数から1日あたりの必要ページ数を自動計算
   - 「時間がないから無理」を「今日は◯ページ読めばOK」に変換
   - 迷いが減り、日々の読書が"タスク化"される

3. **期限の緊急度を"体感できる"UI**
   - 期限が近づくほど書影が色褪せる（賞味期限ビジュアライザー）
   - 数字の締切を"体感"に変えて、先延ばしを防ぐ
   - 一覧を見ただけで「早く読まないとまずい本」が分かる

4. **相互の刺激で継続を支援する（本リリース）**
   - 積読タイムラインで他のユーザーの進捗が見える
   - 一人では挫折しがちな読書を、相互の刺激で習慣化
   - プライバシー配慮: デフォルト非公開、共有設定した本のみ表示

| カテゴリ | 技術 |

### Googleカレンダー連携の実装方法

| フェーズ | 実装方法 |
|----------|----------|
| MVP（簡易版） | Google Calendar の event create URL を生成して遷移（OAuth不要）。予定タイトル / 説明文 / 所要時間を事前入力、日時はユーザーが選択 |
| 本リリース（自動版） | OmniAuth + google-api-client でOAuth認証し、ユーザー指定時間帯に events.insert |
| 将来（空き時間解析版） | freebusy API で空き時間を取得し、最適な時間に自動挿入 |

### ノルマ計算の詳細

残りページ数を $P$（読了対象ページ数 - 現在ページ）、残り日数を $D$（今日を含む残日数。期限当日は $D=1$）とした時、1日あたりの必要ページ数 $N$ を **切り上げ** で算出:

$$N = \lceil P / D \rceil$$

更新タイミング:
- 進捗更新時（現在ページ更新時）に再計算
- 日付切り替わり時（毎日深夜の定期処理）に再計算

### バックグラウンド処理の実装

GitHub Actions（cron）でrake taskを実行:
- ノルマ再計算
- 期限イベント生成（期限3日前、読了など）
- 通知対象抽出（本リリースで送信）

注意点:
- APIキー等はGitHub Secretsで管理
- 定期処理はJST基準で実行（GitHub ActionsのcronはUTCのため、実行時刻をJSTに換算して設定）
- 失敗時はGitHub Actionsの通知で検知し、再実行できる運用を想定

## 非機能要件（とりあえず）

### パフォーマンス
- ページ読み込み時間: 2秒以内
- ノルマ計算: リアルタイム（ユーザーが待たされない）
- 一覧表示: 100冊まで1秒以内

### ユーザビリティ
- 初めて使う人でも3分で本を登録し、ノルマを確認できる
- モバイル対応（レスポンシブデザイン）
- 直感的なUI（説明不要で操作できる）

### 信頼性
- データ損失ゼロ（PostgreSQLの自動バックアップ）
- エラーが起きても適切なエラーメッセージを表示
- 重要な操作（削除など）には確認ダイアログ

### セキュリティ
- パスワードはハッシュ化して保存
- HTTPS通信（Renderで自動対応）
- CSRF対策（Rails標準機能）
- XSS対策（Rails標準機能）

### スケーラビリティ
- 初期は100ユーザー程度を想定
- データベースの最適化（インデックス設定）
- 必要に応じてキャッシュ導入
