# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称
**Yomikiri（ヨミキリ）** - 積読を「今日やること」に変換する読書管理アプリ

### プロダクトコンセプト
- **期限から逆算した行動計画**: 本に賞味期限（読了期限）を設定し、今日読むべきページ数（ノルマ）を自動計算
- **予定化による強制力**: Googleカレンダー連携で読書時間を「予定として見える化」し、意志に頼らず読書時間を確保
- **視覚的プレッシャー**: 期限が迫るほど書影が色褪せる「賞味期限ビジュアライザー」で、先延ばしを防ぐ

### プロダクトビジョン
技術書やビジネス書の「積読（つんどく）」を解消し、確実なスキルアップを支援する。本に賞味期限を設定することで期限意識を持たせ、期限から逆算した「今日のノルマ」を提示することで、読書を具体的な行動に落とし込む。「いつか読もう」を「今日読む」に変え、読書を習慣化させる。

### 目的
- 積読を減らし、購入した本を確実に読了させる
- 「読みたい気持ち」を「読む行動」に変える仕組みを提供
- 期限管理により、情報の賞味期限が切れる前に技術書を読了させる
- 読書時間の予定化により、忙しくても読書を継続できる環境を作る

## 成功指標(KPI)

### プライマリーKPI
- **ユーザー継続率**: 1ヶ月後も使い続けている人が50%以上（2026年6月まで）
- **読了率向上**: アプリを使い始めてから読了数が2倍になる（使用前後3ヶ月の比較）
- **ノルマ達成率**: ユーザーの70%が週に4日以上ノルマを達成（リリース後3ヶ月間の平均）

### セカンダリーKPI
- **アクティブユーザー数**: リリース後3ヶ月で50人（2026年6月まで）
- **累計読了冊数**: リリース後3ヶ月で100冊（全ユーザー合計）
- **カレンダー連携利用率**: 登録された本のうち、60%以上がカレンダーに予定追加される
- **SNSシェア率**: 読了シェア機能の利用率30%以上（本リリース）

### 測定方法

**分析ツール**: データベース内の集計クエリを中心に計測（MVPフェーズ）
- GA4（Google Analytics 4）はMVP検証後、利用状況を見て導入を検討

**計測イベント**（Rails のコントローラーイベントまたはモデルコールバックで記録）:

| KPI | 計測方法 | 集計タイミング |
|-----|---------|---------------|
| 継続率 | `users.where('last_sign_in_at > ?', 1.month.ago)` | 月次 |
| 読了率 | `books.where(status: :completed)` / `books.count` | 週次 |
| ノルマ達成率 | `reading_logs` の `pages_read >= books.daily_quota` の割合 | 日次 |
| カレンダー連携率 | カレンダーリダイレクト数 / 登録書籍数（ログで計測） | 月次 |

**集計責任者**: プロジェクトオーナー（MVP検証フェーズでは手動集計）

**プライバシー**: 個人を特定できない集計値のみを参照し、個人データは分析に使用しない

#### 2. 積読登録

**ユーザーストーリー**:
読書家として、購入した本を積読として登録し、読了期限を設定することで、計画的に読書を進めたい

**受け入れ条件**:
- [ ] 以下の情報を入力して積読を登録できる
  - タイトル（必須）
  - 総ページ数（必須）
  - 読了対象ページ数（必須、初期値＝総ページ数）
  - 読了期限/賞味期限（必須）
  - 現在ページ（必須、初期値＝0）
  - 著者（任意）
  - 書影（任意、未設定時はプレースホルダー画像）
- [ ] 読了対象ページ数は総ページ数以下でバリデーションされる
- [ ] 読了期限は今日以降の日付でバリデーションされる
- [ ] 現在ページは0以上、読了対象ページ数以下でバリデーションされる
- [ ] 登録後、積読一覧画面に遷移する

**優先度**: P0(必須)

**技術仕様**:
```ruby
# Bookモデル（想定）
class Book < ApplicationRecord
  belongs_to :user
  
  validates :title, presence: true, length: { maximum: 255 }
  validates :total_pages, presence: true, numericality: { greater_than: 0 }
  validates :target_pages, presence: true, numericality: { greater_than: 0 }
  validates :current_page, presence: true, numericality: { greater_than_or_equal_to: 0 }
  validates :deadline, presence: true
  validate :deadline_cannot_be_in_the_past
  validate :target_pages_within_total_pages
  validate :current_page_within_target_pages
end
```


#### 8. ノルマ計算・表示

**ユーザーストーリー**:
読書家として、期限から逆算した「今日読むべきページ数」を自動計算してもらい、具体的な行動目標を持ちたい

**受け入れ条件**:
- [ ] ノルマは以下の計算式で算出される: N = ⌈(読了対象ページ数 - 現在ページ) / 残日数⌉
  - 残日数は今日を含む（期限当日は残日数=1）
  - 切り上げで計算
- [ ] ノルマは以下のタイミングで再計算される
  - 進捗更新時
  - 日付が変わったとき（毎日深夜の定期処理）
  - 期限変更時
- [ ] ノルマは一覧画面と詳細画面に表示される
- [ ] 期限を過ぎた場合は、ノルマの代わりに「期限切れ」と表示される

**優先度**: P0(必須)

**計算例**:
```
読了対象ページ数: 300ページ
現在ページ: 120ページ
期限: 2026/03/15（今日: 2026/03/12、残り3日）

残ページ数 P = 300 - 120 = 180ページ
残日数 D = 3日（今日を含む）
ノルマ N = ⌈180 / 3⌉ = 60ページ/日
```

#### 9. Googleカレンダー連携（簡易版）

**ユーザーストーリー**:
読書家として、読書時間をGoogleカレンダーに予定として追加し、読書時間を確保したい

**受け入れ条件**:
- [ ] 詳細画面に「Googleカレンダーに追加」ボタンが表示される
- [ ] ボタンをクリックすると、Googleカレンダーの予定作成画面が開く
- [ ] 以下の情報が事前入力される
  - 予定タイトル: 「【読書】{本のタイトル}」
  - 説明文: 「今日のノルマ: {N}ページ」
  - 所要時間: 15/30/45/60分から選択可能（初期値30分）
- [ ] 日時はユーザーがGoogleカレンダー側で選択
- [ ] OAuth認証は不要（URL生成のみ）
- [ ] MVPではGoogle側の予定変更/削除は追跡しない

**優先度**: P0(必須)

**技術仕様**:
```ruby
# Google Calendar URL生成例
def google_calendar_url(book, duration_minutes = 30)
  params = {
    action: 'TEMPLATE',
    text: "【読書】#{book.title}",
    details: "今日のノルマ: #{book.daily_quota}ページ",
    # duration は HHMM 形式（例: 30分 → "0030"）
    duration: format('%02d%02d', duration_minutes / 60, duration_minutes % 60)
  }
  "https://calendar.google.com/calendar/render?#{params.to_query}"
end
```

#### 10. 賞味期限ビジュアライザー（CSS版）

**ユーザーストーリー**:
読書家として、期限が近い本を視覚的に把握し、優先順位を感覚的に理解したい

**受け入れ条件**:
- [ ] 一覧画面の書影に対して、期限までの日数に応じてCSSエフェクトが適用される
- [ ] エフェクトの段階:
  - 7日以下: セピア/透明度：弱（filter: sepia(30%) opacity(90%)）
  - 3日以下: セピア/透明度：中（filter: sepia(60%) opacity(70%)）
  - 1日以下: セピア/透明度：強（filter: sepia(100%) opacity(50%)）
- [ ] 期限を過ぎた本は最大エフェクト（filter: sepia(100%) opacity(30%)）
- [ ] エフェクトはCSSのみで実装（JavaScriptは不要）
- [ ] 読了済みの本にはエフェクトを適用しない

**優先度**: P0(必須)

**技術仕様**:
```css
/* app/assets/stylesheets/books.css */
/* BEM 修飾クラス: deadline_class メソッドが返す値をそのまま class に付与 */
.book-cover--days-7  { filter: sepia(30%);  opacity: 0.90; }
.book-cover--days-3  { filter: sepia(60%);  opacity: 0.70; }
.book-cover--days-1  { filter: sepia(100%); opacity: 0.50; }
.book-cover--overdue { filter: sepia(100%); opacity: 0.30; }
```

- [ ] 取得できる情報: タイトル、著者、総ページ数、書影URL
- [ ] 取得できない項目は手入力で補完できる
- [ ] APIエラー時は適切なエラーメッセージを表示

**優先度**: P1(重要)

**技術仕様**:
- openBD API: https://openbd.jp/
- APIキー不要
- エンドポイント: `GET https://api.openbd.jp/v1/get?isbn={isbn}`

#### 15. メール通知機能

**ユーザーストーリー**:
読書家として、期限が近づいたときにメールで通知を受け取り、読書を思い出したい

**受け入れ条件**:
- [ ] 期限3日前の00:00（JST）にリマインドメールが送信される
- [ ] 期限3日前の判定: (期限日 - 3日)のJST 00:00基準
- [ ] 同一ユーザー・同一本につき1回のみ送信
- [ ] メール内容: 本のタイトル、残り日数、今日のノルマ、詳細ページへのリンク
- [ ] 通知設定でON/OFFを切り替えられる

**優先度**: P1(重要)

**技術仕様**:
- ActionMailer + SendGrid
- GitHub Actionsのcronで毎日00:00（UTC 15:00）に実行

#### 16. 読了シェア機能（OGP対応）

**ユーザーストーリー**:
読書家として、読了したときにSNSでシェアし、達成感を共有したい

**受け入れ条件**:
- [ ] 読了時にシェア用ページが生成される
- [ ] シェアページにOGPメタタグが設定される
- [ ] 表示内容: タイトル、読了までの日数、読了日、一言コメント（任意）
- [ ] X（Twitter）、Facebook、LINEでシェアできる
- [ ] シェアページは公開/非公開を選択できる

**優先度**: P1(重要)

#### 17. 積読タイムライン機能

**ユーザーストーリー**:
読書家として、他のユーザーの積読状況や進捗を見て、モチベーションを高めたい

**受け入れ条件**:
- [ ] デフォルトは非公開。本ごとに共有設定をONにした場合のみタイムラインに表示
- [ ] 公開される情報: 本のタイトル、期限、進捗（%）のみ（メモ等は非公開）
- [ ] 表示名: ニックネーム（実名不要）
- [ ] 表示形式: イベント単位
  - 新規登録時: 「{ユーザー名}さんが『{タイトル}』を登録しました」
  - 期限3日前: 「{ユーザー名}さんの『{タイトル}』があと3日です！」
  - 読了時: 「{ユーザー名}さんが『{タイトル}』を読了しました🎉」
  - 延長時: 「{ユーザー名}さんが『{タイトル}』の期限を延長しました」
- [ ] タイムラインは最新50件まで表示

**優先度**: P1(重要)

#### 18. 読書スピード計測

**ユーザーストーリー**:
読書家として、自分の読書スピードを計測し、より正確なノルマと所要時間を知りたい

**受け入れ条件**:
- [ ] 詳細画面に「読書タイマー」ボタンが表示される
- [ ] タイマーで読書時間を計測できる
- [ ] 読書後、読んだページ数を入力すると、1ページあたりの時間が記録される
- [ ] 過去の計測データから平均読書スピードが算出される
- [ ] ノルマ表示時、所要時間も表示される（例: 「60ページ（約30分）」）

**優先度**: P1(重要)

#### 19. バックグラウンド処理

**ユーザーストーリー**:
システム管理者として、毎日自動的にノルマ再計算と通知送信が実行されるようにしたい

**受け入れ条件**:
- [ ] GitHub Actionsのcronで毎日00:00（JST）に以下を実行
  - ノルマ再計算
  - 期限イベント生成（期限3日前、読了など）
  - 通知対象抽出・送信
- [ ] APIキー等はGitHub Secretsで管理
- [ ] 失敗時はGitHub Actionsの通知で検知できる
- [ ] 手動で再実行できる

**優先度**: P1(重要)

**技術仕様**:
```yaml
# .github/workflows/daily_tasks.yml
name: Daily Background Tasks
on:
  schedule:
    - cron: '0 15 * * *'  # 毎日00:00 JST (UTC 15:00)
  workflow_dispatch:  # 手動実行も可能

jobs:
  run_tasks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Ruby
        uses: ruby/setup-ruby@v1
      - name: Install dependencies
        run: bundle install
      - name: Run daily tasks
        run: bundle exec rake daily:all
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          SENDGRID_API_KEY: ${{ secrets.SENDGRID_API_KEY }}
```

## 非機能要件

### パフォーマンス
- **ページ読み込み時間**: 2秒以内（初回は3秒以内）
- **ノルマ計算**: リアルタイム（ユーザーが待たされない、100ms以内）
- **一覧表示**: 100冊まで1秒以内に表示
- **データベースクエリ**: N+1問題を回避し、includesで関連データを一括取得

### ユーザビリティ
- **学習コスト**: 初めて使う人でも3分で本を登録し、ノルマを確認できる
- **モバイル対応**: レスポンシブデザインで、スマートフォンでも快適に操作できる
- **直感的なUI**: 説明不要で操作できる（アイコン、カラーコーディング、適切なラベル）
- **アクセシビリティ**: 代替テキスト、キーボード操作、十分なコントラスト比

### 信頼性
- **データ損失ゼロ**: PostgreSQLの自動バックアップ（Neonの機能を利用）
- **エラーハンドリング**: エラーが起きても適切なエラーメッセージを表示し、ユーザーを誘導
- **確認ダイアログ**: 重要な操作（削除など）には確認ダイアログを表示
- **トランザクション**: データの整合性を保つため、必要な箇所でトランザクションを使用

### セキュリティ
- **パスワード管理**: bcryptでハッシュ化して保存
- **HTTPS通信**: Renderで自動対応
- **CSRF対策**: Rails標準機能（authenticity_token）
- **XSS対策**: Rails標準機能（HTMLエスケープ）
- **SQLインジェクション対策**: ActiveRecordを使用し、生SQLは避ける
- **認証トークン**: APIキー、OAuth tokenはGitHub Secretsで管理

### スケーラビリティ
- **初期想定**: 100ユーザー、1ユーザーあたり平均20冊
- **データベース最適化**: インデックス設定（user_id, deadline, status）
- **キャッシュ**: 必要に応じてフラグメントキャッシュを導入（本リリース以降）
- **CDN**: 静的アセット（画像、CSS、JS）はCloudflareやCloudinaryを検討（将来）

### 保守性
- **コード品質**: RuboCopで静的解析、コーディング規約を遵守
- **テスト**: RSpecで単体テスト、統合テスト、システムテストを実装
- **ドキュメント**: README、API仕様書、ER図を常に最新に保つ
- **バージョン管理**: Gitで管理、意味のあるコミットメッセージ

## リスクと対策

### リスク1: ユーザーが期限を延長し続けて、機能の意味がなくなる

**対策**:
- 延長回数を目立つ位置に表示し、心理的プレッシャーをかける
- 本リリースで延長イベントをタイムラインに表示し、可視化する
- 週次サマリーで延長回数をフィードバック（将来）

### リスク2: ノルマが大きすぎて、逆にモチベーションが下がる

**対策**:
- 期限設定時に「現実的な期限を設定してください」とガイダンスを表示
- 読書する曜日/頻度を設定し、より現実的なノルマを計算（本リリース）
- 期限を簡単に延長できる仕組みを用意

### リスク3: Googleカレンダー連携を使わないユーザーが多い

**対策**:
- MVPでは簡易版（URL生成のみ）で実装し、利用率を測定
- 利用率が低い場合、他のカレンダーサービスや代替案を検討
- UIで「カレンダーに追加すると読書時間を確保しやすくなります」とメリットを訴求

### リスク4: 積読タイムラインでプライバシーの問題が発生

**対策**:
- デフォルトは非公開、共有設定は本ごとに明示的にON
- 公開情報は最小限（タイトル、期限、進捗のみ）
- ニックネーム表示で実名不要

### リスク5: バックグラウンド処理（GitHub Actions）が失敗する

**対策**:
- GitHub Actionsの通知機能で失敗を検知
- 手動での再実行を可能にする（workflow_dispatch）
- 本リリース以降、重要な処理はsolid_queueへ移行を検討
