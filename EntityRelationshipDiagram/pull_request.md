### 本サービスの概要（700文字以内）

Yomikiriは、技術書やビジネス書の「積読（つんどく）」に悩む人のための読書管理アプリです。

**課題：** エンジニアや自己研鑽に励むビジネスパーソンは、良書を次々と購入するものの、「読みたい気持ちはあるのに時間が作れない」という悩みを抱えがちです。既存の読書管理アプリは「記録」が中心で、「読ませる」ための仕組みが不足しています。

**解決策：** 本サービスは、本に「賞味期限（読了期限）」を設定し、期限から逆算した「今日のノルマ（必要ページ数）」を提示することで、読書を具体的な行動に変換します。さらに、Googleカレンダー連携により読書時間を予定として確保し、「いつ読むか」を明確にします。

**主な機能：** 積読登録（タイトル・総ページ数・読了期限の設定）、ノルマ計算（残ページ数÷残日数で1日の必要読書量を自動算出）、賞味期限ビジュアライザー（期限が近づくと書影が色褪せ、緊急度を視覚化）、Googleカレンダー連携（ワンクリックで読書予定を作成）。

**想定ユーザー：** プログラミング初学者・現役エンジニア、資格試験に励むビジネスパーソン、積読に罪悪感を感じている読書家。

### MVPで実装する予定の機能

- 会員登録・ログイン機能（Devise認証）
- 積読一覧表示機能（期限が近い順にソート）
- 積読登録機能（書影は任意、未設定時はプレースホルダー表示）
- 積読詳細表示機能（進捗・ノルマ確認）
- 進捗更新機能（「今日読んだページ数」入力で現在ページに反映／現在ページ直接入力も可）
- 読書ステータス管理機能（未読・読書中・読了の切り替え／到達時は「読了にする」を強調）
- 読了期限の変更（延長）機能（延長回数の表示）
- Googleカレンダー連携機能（MVP：予定作成画面へのリンク生成、OAuth不要）
- 賞味期限ビジュアライザー機能（CSS版：7日/3日/1日の段階で色褪せ）
- マイページ表示機能（読了履歴・アカウント設定の統合ページ）
- パスワード変更機能（ログイン後にマイページから変更）
- メールアドレス変更機能（確認メールによる本人確認→変更完了→再ログイン誘導）

### テーブル詳細

#### usersテーブル【MVP】
- id : 各ユーザーを一意に識別する
- email : ログイン認証に使用。Deviseが管理する
- encrypted_password : Deviseが自動で暗号化・管理する。アプリ側では直接扱わない
- nickname : マイページの表示名。未設定時はメールアドレスをフォールバック表示する。本リリースの積読タイムラインでも実名の代わりに表示される / 例: `たろう`
- google_uid : OAuth認証時にGoogleが発行するユーザー識別子 ※本リリース
- google_access_token : GoogleカレンダーAPIへのリクエストに使用するアクセストークン ※本リリース
- google_refresh_token : アクセストークンの期限切れ時に再取得するためのリフレッシュトークン ※本リリース
- google_token_expires_at : アクセストークンの有効期限。超過時にリフレッシュトークンで再取得する ※本リリース
- created_at : レコード作成日時
- updated_at : レコード更新日時

#### booksテーブル【MVP】
- id : 各積読本を一意に識別する
- user_id : この本を登録したユーザーへの参照
- title : 本のタイトル / 例: `リーダブルコード`
- author : 著者名。任意入力 / 例: `Dustin Boswell`
- total_pages : 本全体のページ数。登録時に入力する / 例: `260`
- target_pages : ノルマ計算の基準となる読了対象ページ数。索引や付録を除いた範囲を設定できる。初期値は total_pages / 例: `240`
- current_page : 進捗更新で増加する現在ページ。ノルマ計算に使用される / 例: `120`
- deadline : 本に設定する「賞味期限（読了期限）」。ノルマ計算と賞味期限ビジュアライザーの基準 / 例: `2026-03-15`
- status : 読書の進行状態を表すenum。`0:未読 → 1:読書中 → 2:読了` の順に遷移する。初回の進捗更新で自動的に読書中へ変移し、「読了にする」ボタン押下で読了になる
- cover_image : 書影画像のURL。未設定時はプレースホルダー画像を表示する
- extension_count : 期限を延長した回数。詳細画面に表示し「先延ばしの見える化」として機能する
- completed_at : 「読了にする」を押した日時。マイページの読了履歴に読了日として表示される
- is_public : 積読タイムラインへの公開可否フラグ。trueにした本のみタイムラインにイベントが生成される ※本リリース
- created_at : レコード作成日時
- updated_at : レコード更新日時

#### timeline_eventsテーブル【本リリース】
- id : 各タイムラインイベントを一意に識別する
- user_id : イベントを生成したユーザーへの参照
- book_id : イベントが紐づく本への参照
- event_type : タイムラインに表示するイベントの種別。`0:新規登録 / 1:期限3日前 / 2:読了` の3種類。「期限3日前」は同一ユーザー・同一本につき1回のみ発火する
- progress_percentage : イベント発火時点の進捗率のスナップショット。books側の値が変わっても過去のタイムラインに影響しないよう保存する / 例: `50.5`（%）
- published_at : タイムラインの表示順に使用するイベント公開日時
- created_at : レコード作成日時
- updated_at : レコード更新日時

#### reading_speed_recordsテーブル【本リリース】
- id : 各計測記録を一意に識別する
- user_id : 計測を行ったユーザーへの参照
- book_id : 計測対象の本への参照
- pages_read : タイマー計測中に読んだページ数 / 例: `10`
- time_spent_seconds : 読書にかかった時間（秒単位）。`time_spent_seconds ÷ pages_read` で1ページあたりの平均読書時間を算出し、時間⇄ページのノルマ換算精度を向上させる / 例: `1800`（30分）
- recorded_at : 計測を行った日時
- created_at : レコード作成日時
- updated_at : レコード更新日時

#### reading_logsテーブル【本リリース】
- id : 各読書日ログを一意に識別する
- user_id : 読書を行ったユーザーへの参照
- book_id : 読書した本への参照
- read_date : 進捗更新（current_page変更）が行われた日付。1ユーザー・1冊・1日につき1レコードをupsertする設計。MVPでは books.updated_at で代用するが、期限変更・書影変更でも updated_at が更新されてしまうため、本リリースでこのテーブルに移行し正確に集計する
- created_at : レコード作成日時
- updated_at : レコード更新日時

#### reading_preferencesテーブル【本リリース】
- id : 各読書設定を一意に識別する
- user_id : 設定の持ち主であるユーザーへの参照（1ユーザーにつき1レコード）
- days : 読書する曜日をカンマ区切りで保持する。1NFの観点では中間テーブルへの分離が正規形だが、実装コスト優先で意図的な非正規化として文字列で保持する / 例: `"月,水,金"`
- frequency : 週あたりの読書日数。daysと組み合わせて「読む日」のみで逆算したノルマ計算に使用する / 例: `3`（週3日）
- preferred_time_start : Googleカレンダーへ読書スロットを自動挿入する際の開始時刻 / 例: `19:00`
- preferred_time_end : Googleカレンダーへ読書スロットを自動挿入する際の終了時刻 / 例: `21:00`
- created_at : レコード作成日時
- updated_at : レコード更新日時
